# DUUI Multimodal Pipeline Architecture

This architecture is fundamentally a multimodal, microservice-based NLP pipeline built on top of Apache UIMA (Unstructured Information Management Architecture). It solves the classic problem of running heavy, Python-based Machine Learning models (like Whisper or Pyannote) within a strict, Java-based enterprise framework.

## 1. The Core Data Structure: UIMA CAS and Views

The lifeblood of the pipeline is the CAS (Common Analysis Structure). The CAS is an object that travels through the pipeline, holding both the raw data and the metadata (annotations) generated by the engines.

To handle multimodal data (audio, text, and video), the CAS uses Views (Sofas — Subject of Analysis). Views act as isolated namespaces within the same CAS:

- **AudioView**: Holds the raw `.wav` or `.mp3` file as a Base64 encoded string.
- **TextView**: Holds the plain text transcript generated by WhisperX, along with all NLP annotations (Sentences, Tokens, Speaker Segments).
- **EmotionView**: Holds the final sentiment and emotion annotations.

By routing data across Views (e.g., `.withSourceView("AudioView").withTargetView("TextView")`), the pipeline prevents downstream components from accidentally overwriting the original media files or causing cross-modality corruption.

## 2. The Communication Layer: The Lua-HTTP Bridge

Because UIMA operates in Java and the ML models (WhisperX, SpaCy, pyannote) operate in Python, passing memory-heavy UIMA CAS objects directly is impossible. DUUI solves this via a REST-based Lua Serialization Bridge.

When the `DUUIComposer` passes the CAS to a specific Docker component, the following exact lifecycle occurs:

1. **Handshake**: The Java `DUUIDockerDriver` makes a GET request to the Python container's `/v1/communication_layer` endpoint. The container returns a `.lua` script.
2. **Serialization (Java → JSON)**: The Java engine executes the `serialize()` function in the Lua script. This script reaches into the specific UIMA View, extracts only the required data (e.g., pulling the base64 audio string from `AudioView`), and formats it into a lightweight JSON payload.
3. **Inference**: The JSON is POSTed to the Python container's `/v1/process` endpoint. A FastAPI server parses it, runs the ML model (e.g., PyTorch on GPU), and returns a JSON response.
4. **Deserialization (JSON → Java)**: The Java engine executes the `deserialize()` Lua function. This maps the JSON results directly into strictly typed UIMA FeatureStructures (as defined in your `MultimodalIdentityTypeSystem.xml` or `dkpro-core-types.xml`) and injects them into the target View's index.

## 3. Step-by-Step Pipeline Execution Flow

When you execute `composer.run(jcas)`, the pipeline processes the data sequentially through the defined topology.

### Step 1: WhisperXContainer (ASR & Alignment)
- **Source**: AudioView | **Target**: TextView
- **Action**: The container decodes the base64 audio and runs the Whisper V2/V3 model to generate a transcript. It then runs a forced alignment model to get millisecond-accurate timestamps for every single word.
- **Output**: The Lua script writes the full continuous string to `TextView:DocumentText`. It then creates an `org.texttechnologylab.annotation.type.AudioToken` for every word, populating the `begin`, `end`, `timeStart`, and `timeEnd` features.

### Step 2: SpaCyContainer (NLP Processing)
- **Source**: TextView | **Target**: TextView
- **Action**: Reads the plain text transcript from the TextView. It runs standard NLP tokenization and Sentence Boundary Detection (SBD).
- **Output**: Creates DKPro `Sentence` and `Token` annotations. Because it writes to the same view as Whisper, the text boundaries (`begin`, `end`) of these sentences overlap perfectly with the `AudioToken` boundaries.

### Step 3: VoiceIdentityContainer (Speaker Diarization)
- **Source**: AudioView | **Target**: TextView
- **Action**: Reads the raw audio again. Uses `pyannote.audio` to perform speaker diarization (clustering acoustic features to determine who spoke when).
- **Output**: Generates `org.texttechnologylab.annotation.audio.SpeakerSegment` annotations. Since diarization is purely acoustic, these annotations are written with text bounds `(0,0)`, relying entirely on their `timeStart` and `timeEnd` features.

### Step 4: AudioSentenceContainer (The Multimodal Merger)
- **Source**: TextView | **Target**: TextView
- **Action**: This is a purely logical container. It reads the DKPro `Sentence` boundaries, the Whisper `AudioToken`s, and the Pyannote `SpeakerSegment`s.
- **Merge Logic**: For a given Sentence, it looks up all `AudioToken`s that fall within its text bounds to determine the minimum `timeStart` and maximum `timeEnd`. It then checks which `SpeakerSegment` temporally overlaps the most with that window.
- **Output**: Creates an `org.texttechnologylab.annotation.type.AudioSentence`. This is a unified anchor containing the text span, the absolute video timestamps, and implicitly links the speaker.

### Step 5: TextEmotionContainer & AudioEmotionContainer
- **Source**: TextView / AudioView | **Target**: EmotionView
- **Action**: Finally, the pipeline forks. The TextEmotion engine pulls the `AudioSentence` text and runs text-based sentiment analysis (e.g., GerVADER or a Transformer). The AudioEmotion engine pulls the raw audio sliced by those exact timestamps to calculate acoustic valence/arousal (using models like HSEmotion or Wav2Vec).
- **Output**: Both write `org.texttechnologylab.annotation.emotion.Emotion` annotations into the `EmotionView`. The Lua script links these annotations back to the original `AudioSentence` via the `reference` feature, ensuring the emotion is perfectly tied to the text, the speaker, and the specific timeframe in the video.
